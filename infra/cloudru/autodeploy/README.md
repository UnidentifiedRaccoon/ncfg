# Автодеплой Cloud.ru

Push в `main` запускает `.github/workflows/deploy.yml`. GitHub проверяет тесты
развёртывания и сохранения старых Next.js assets, затем перемещает служебную ветку
`cloudru-production` на проверенный коммит. Pull request выполняет только проверки.
На ВМ таймер проверяет обе ветки примерно раз в минуту и принимает только их
совпадающий SHA. После сборки он повторно проверяет, что коммит всё ещё актуален.
Не отправлять изменения в `cloudru-production` вручную.

Сборка выполняется на `ncfg-app-01`: отдельный BuildKit ограничен 4 ГБ памяти
и 1,5 CPU; этапы выполняются последовательно, кеш — 3 ГБ на диске данных
`/srv/ncfg/buildkit-cache`.
Профиль Buildx находится в `/etc/ncfg/autodeploy-docker`, вне закрытого home.
Перед каждой новой попыткой релиза supervisor очищает неиспользуемый кеш
**только default builder**, старше 24 часов, с резервом кеша 1 ГБ:
`docker buildx prune --builder default --filter until=24h --reserved-space 1GB --force`.
Кеш отдельного `ncfg-autodeploy`, образы, контейнеры отката, volumes и данные
приложения эта команда не удаляет. После очистки свободное место проверяется
повторно. Если осталось менее 4 ГиБ, сборка не начинается; записывается ошибка
`insufficient_disk` с фактическим и требуемым объёмом.
Сайт получает прежние immutable assets за 21 день. Секрет чтения CMS передаётся
только через BuildKit secret. Источник runtime-настроек описан ниже.
Для GitHub не нужны SSH-ключ, Cloud.ru API key или секреты приложения.

Перед очисткой кеша supervisor выполняет ротацию релизов. Для сайта и CMS
отдельно сохраняются текущий контейнер и две последние остановленные версии
`*-release-*` по времени остановки; явно записанные контейнеры отката защищены
дополнительно. Релиз только сайта сохраняет запись об откате CMS.

Удаляются только остановленные контейнеры `ncfg-cloudru-{web,cms}-release-*`
с меткой `io.ncfg.autodeploy=true`, которые вышли за этот предел. Контейнеры
`*-failed-*` с той же меткой удаляются спустя 24 часа после остановки. Старые
контейнеры миграции без метки, все работающие сервисы и volumes не затрагиваются.
Образы удаляются только с меткой автодеплоя, согласованными тегом/SHA и возрастом
от 24 часов, если на них не ссылается ни один фактически существующий контейнер
и они не указаны в активном состоянии. Дополнительный тег оператора защищает
образ. Поэтому недавно устаревший образ может прожить ещё сутки без контейнера.

Ротация использует общий `deploy.lock`, запрещена при незавершённой транзакции
и перепроверяет кандидатов перед каждым удалением. Используются только адресные
`docker container rm` и `docker image rm`, без `--force`, `--volumes` или общего
prune. Неизвестное состояние или нездоровый текущий сервис означают пропуск
очистки; обычный деплой при этом может исправить неисправный сервис.

Очистка выполняется перед сборкой, после успешного релиза и при последующих
idle-запусках таймера. Ошибка Docker при preflight останавливает сборку и видна
в Actions как `retention_cleanup_failed`. Ошибка обслуживания после успешного
релиза записывается в журнал и повторяется на следующем запуске таймера; она
не откатывает уже проверенную версию. Каталоги исходников и bare Git на диске
данных `/srv/ncfg` в эту ротацию не входят.

BuildKit подключён к внутренней сети приложения и к bridge для загрузки пакетов.
При сборке адрес CMS берётся
из текущего контейнера: обращение ВМ к собственному публичному IP недоступно.
Проверка на ВМ проходит через `127.0.0.1:443` с настоящим доменом и обычной
проверкой TLS-сертификата; GitHub дополнительно проверяет публичный DNS-маршрут.

CMS пересобирается при изменении `apps/cms` или `docker/cms`. Если меняется только
её окружение, используется прежний образ с новыми настройками. До её переключения
создаётся и проверяется внешняя резервная копия. Web пересобирается для каждого
одобренного коммита. При перезапуске контейнера возможен короткий перерыв.

Ошибка сборки оставляет старый сайт запущенным. Ошибка readiness или публичной
проверки возвращает предыдущие контейнеры. Незавершённая операция восстанавливается
по журналу после перезапуска службы. Откат контейнеров **не откатывает схему/данные
БД**: несовместимые миграции Strapi требуют отдельного плана и окна работ.

GitHub каждые 10 секунд читает `https://ncfg.ru/deployment-status.json`.
Этот JSON обслуживается самим Caddy независимо от контейнера сайта. Он содержит
только SHA, состояние, этап, время, код ошибки и числовые показатели диска;
исключения, логи, конфигурация и секреты в него не копируются. Ответ имеет
`Cache-Control: no-store` и `X-Robots-Tag: noindex, nofollow`.

Ошибка нужного SHA сразу завершает шаг Actions с аннотацией и кратким отчётом;
при нехватке диска в них указаны свободный и требуемый объёмы. Старые ошибки
других SHA игнорируются. Если supervisor не подтвердил запуск или канал статуса
пропал на 3 минуты, ожидание завершается явной ошибкой. Для активной сборки
сохраняется общий лимит 40 минут. Таймер ВМ может добавить до минуты до начала
проверки нового релиза.
Статус обновляется при смене этапов, а не как heartbeat: при аварийной остановке
процесса без записи ошибки последняя стадия может оставаться `running` до общего
таймаута. Обычные исключения, включая недостаток места, публикуются сразу.

Успех требует состояния `succeeded`, точного SHA на
`https://ncfg.ru/deployment.json` и health сайта и CMS. Поэтому зелёный workflow
подтверждает публичный запуск, а не только передачу задания. Отправка тестовых
писем и заявок не производится.

## Таймаут получения исходников

Для `git fetch` задан отдельный лимит 600 секунд; остальные команды сохраняют
свои лимиты. При таймауте checkout останавливается до сборки и активации.
В журнал выводятся только название операции и лимит, а в `failed.json` и публичный
статус — код `git_fetch_timeout` и `timeoutSeconds`. Аргументы команды, stdout,
stderr и текст исключения не публикуются. GitHub CI показывает эту причину явно.

Автоматического повтора и удаления Git lock-файлов нет. Перед ручным повтором
оператор проверяет отсутствие активного деплоя и Git-процессов, затем разбирает
оставшиеся блокировки, включая `git/shallow.lock`. Один лишь новый таймаут не
устраняет существующую блокировку. Эта версия supervisor требует отдельной
установки на ВМ; изменение репозитория не обновляет серверный файл.

## Управление

```sh
sudo systemctl status ncfg-autodeploy.timer ncfg-autodeploy.service
sudo journalctl -u ncfg-autodeploy.service -n 30 --no-pager
sudo cat /srv/ncfg/autodeploy/active.json
sudo cat /srv/ncfg/autodeploy/failed.json
sudo env DOCKER_CONFIG=/etc/ncfg/autodeploy-docker python3 /usr/local/lib/ncfg-autodeploy/deploy.py --retention-plan
```

`--retention-plan` печатает план без удаления и без восстановления транзакций.
Для ручного применения проверенного плана используется `--retention-apply`;
он берёт тот же lock и заново проверяет состояние, а не доверяет старому списку.
После очистки фактически освобождённое место проверяют через `df`: размеры
образов нельзя складывать напрямую из-за общих слоёв и ссылок кеша сборщика.

В журнал попадают только этапы, SHA и тип ошибки. Подробные логи сборки находятся
в `/srv/ncfg/autodeploy/{web,cms}-build.log` и доступны только root. Не публиковать
их целиком: сборка может содержать данные CMS, даже если токен замаскирован.

Остановить новые публикации: `sudo systemctl stop ncfg-autodeploy.timer`.
Уже выполняющийся деплой продолжится; не прерывать его в момент переключения.
После исправления сбоя оператор сохраняет `failed.json` под архивным именем и
повторно запускает службу. Повторный workflow того же SHA сам по себе не удаляет
зафиксированную ошибку и не запускает очистку каждую минуту. Новые коммиты
разрешены независимо от старого сбоя.
Две предыдущие версии сервисов и исходники сохраняются; следить за местом на дисках.
Не применять общий `docker system prune` и не удалять данные PostgreSQL.

Supervisor установлен отдельно: `/usr/local/lib/ncfg-autodeploy/deploy.py`.
Рядом устанавливается модуль `secret_manager.py`; при обновлении сначала
установите модуль, затем supervisor, под общим `deploy.lock`.
Изменение этого файла в Git не обновляет службу автоматически. Его новую версию
сначала проверяют тестами и устанавливают через административный SSH-доступ.

При обновлении с версии без публичного статуса сначала на ВМ запускают
`sudo python3 install_status.py`, затем устанавливают проверенный `deploy.py`
с сохранением прежнего файла для отката. Установку supervisor выполняют между
деплоями: останавливают только timer, убеждаются, что service завершён, и
используют `/srv/ncfg/autodeploy/deploy.lock`. После обновления запускают службу
для публикации статуса текущего SHA, возвращают timer и проверяют его состояние.
До push нового workflow проверяют
статус текущего SHA через HTTPS. Полный `install.sh` нужен при первоначальной
настройке; для обновления supervisor builder пересоздавать не требуется.

`install_status.py` принимает только известную конфигурацию production Caddy,
проверяет кандидата, сохраняет приватную резервную копию и добавляет ровно один
маршрут JSON. Он использует существующий bind mount `/config`, сохраняет inode
Caddyfile и применяет конфигурацию через SIGUSR1 (Caddy 2.11+). Контейнер Caddy
не перезапускается, admin API остаётся выключенным. При ошибке проверки
восстанавливается прежняя конфигурация. Повторный запуск сохраняет текущий статус.

Локальная проверка контракта ошибки, отката конфигурации и ожидания Actions:
`python3 -m unittest discover -s infra/cloudru/autodeploy -p 'test_*.py'`.
Для проверки нехватки места используются тестовые значения; заполнять диск
production или публиковать фиктивную ошибку в рабочем endpoint не нужно.

Изменения лимитов/конфигурации BuildKit требуют пересоздать только builder
после окончания сборки: `docker buildx rm --keep-state ncfg-autodeploy`, затем
повторить `install.sh` с профилем `DOCKER_CONFIG=/etc/ncfg/autodeploy-docker`.
Кеш при этом сохраняется; рабочие контейнеры приложения не пересоздаются.
Workflow перед ручным запуском должен быть выбран на ветке `main`.

DNS и Postbox остаются в Yandex; production-развёртывание больше не использует
Yandex Serverless/Registry/Lockbox. Старые preview, registry-retention,
coldstart-smoke и HR seed workflows перенесены в `.github/retired-workflows`,
где GitHub Actions их не запускает. Старые скрипты ротации Bitrix24 через
Lockbox и очистки Yandex Registry прекращают работу без изменений ресурсов.


## Secret Management

Интеграция включается только при наличии root-only файла
`/etc/ncfg/secret-manager.json`. Без него supervisor сохраняет прежнее чтение
`/etc/ncfg/runtime/{web,cms}.json`. Это совместимость для поэтапного переноса,
а не автоматический fallback при отказе Cloud.ru.

Конфигурация содержит `projectId`, абсолютный `credentialsFile` и `bindings`
с двумя элементами `web` и `cms`. Каждый элемент задаёт `path` (`ncfg/production-web`
или `ncfg/production-cms`) и положительный номер `version`. Файл credentials
содержит `keyId` и `secret` сервисного аккаунта `ncfg-secret-runtime`.
Оба файла должны принадлежать root, иметь режим 0600 и находиться в каталоге 0700.
Значения ключей нельзя передавать аргументами команд, печатать или добавлять в Git.

Аккаунт runtime получает `scsm.user` только на два production-секрета.
Разработке доступен отдельный `ncfg/development`, без production write-token,
почтовых/CRM-ключей и паролей CMS/БД.

Перед новой сборкой supervisor обменивает ключ на часовой IAM-токен и читает
закреплённые версии через Secret Management v2 API. Проверяются проект, путь,
номер и состояние версии, JSON и строковые значения переменных. Redirect и
ошибки авторизации/формата останавливают деплой до checkout и переключения
контейнеров. Содержимое API-ошибок и credentials в журнал не попадает.
Работающий релиз продолжает обслуживать запросы.

Значения читаются в память; файлы `/etc/ncfg/runtime` не перезаписываются.
Первоначальные файлы остаются зафиксированной точкой ручного отката. Они не
обновляются при последующих ротациях Secret Management. Перед включением
конфигурации необходимо прочитать реальные версии и проверить точное совпадение
с текущим runtime, проверить отказ dev-аккаунту в доступе к production и сохранить
независимую зашифрованную копию.

Для ручного возврата к файловой конфигурации: между деплоями, под `deploy.lock`,
переименовать `/etc/ncfg/secret-manager.json` в приватный архивный файл. Не удалять
ключи и секреты до проверки восстановления. Обычный перезапуск существующих
Docker-контейнеров продолжает использовать их сохранённое окружение.

Изменения кода и наличие этого раздела не доказывают, что интеграция уже включена
на ВМ: фактическое переключение фиксируется в приватном отчёте миграции.

### Применение новой версии секрета

После проверки новой версии измените её номер в `/etc/ncfg/secret-manager.json`.
При следующем разрешённом деплое CMS сравнивает желаемое окружение с окружением
работающего контейнера. Если код CMS не изменился, но значения или набор переменных
изменились, деплой использует прежний образ CMS с новым окружением. Перед заменой
CMS по-прежнему обязательна проверенная резервная копия.

Чтобы применить закреплённые версии сразу, без нового Git-коммита, оператор запускает:

```bash
sudo env DOCKER_CONFIG=/etc/ncfg/autodeploy-docker python3 /usr/local/lib/ncfg-autodeploy/deploy.py --refresh-secrets
```

Команда использует обычную блокировку, сборку сайта, проверки готовности и откат.
Она также явно повторяет ранее неудачный деплой текущей разрешённой ревизии.
Каждая активация имеет свой идентификатор транзакции, поэтому сбой ротации на той
же ревизии кода восстанавливает прежние контейнеры. Таймер сам по себе не запускает
ротацию на неизменившейся ревизии.

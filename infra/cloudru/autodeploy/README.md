# Автодеплой Cloud.ru

Push в `main` запускает `.github/workflows/deploy.yml`. GitHub проверяет тесты
развёртывания и сохранения старых Next.js assets, затем перемещает служебную ветку
`cloudru-production` на проверенный коммит. Pull request выполняет только проверки.
На ВМ таймер проверяет обе ветки примерно раз в минуту и принимает только их
совпадающий SHA. После сборки он повторно проверяет, что коммит всё ещё актуален.
Не отправлять изменения в `cloudru-production` вручную.

Сборка выполняется на `ncfg-app-01`: отдельный BuildKit ограничен 4 ГБ памяти
и 1,5 CPU; этапы выполняются последовательно, кеш — 3 ГБ на диске данных
`/srv/ncfg/buildkit-cache`.
Профиль Buildx находится в `/etc/ncfg/autodeploy-docker`, вне закрытого home.
Перед каждой новой попыткой релиза supervisor очищает неиспользуемый кеш
**только default builder**, старше 24 часов, с резервом кеша 1 ГБ:
`docker buildx prune --builder default --filter until=24h --reserved-space 1GB --force`.
Кеш отдельного `ncfg-autodeploy`, образы, контейнеры отката, volumes и данные
приложения эта команда не удаляет. После очистки свободное место проверяется
повторно. Если осталось менее 4 ГиБ, сборка не начинается; записывается ошибка
`insufficient_disk` с фактическим и требуемым объёмом.
Сайт получает прежние immutable assets за 21 день. Секрет чтения CMS передаётся
только через BuildKit secret; runtime-настройки остаются в `/etc/ncfg/runtime`.
Для GitHub не нужны SSH-ключ, Cloud.ru API key или секреты приложения.

BuildKit подключён к внутренней сети приложения и к bridge для загрузки пакетов.
При сборке адрес CMS берётся
из текущего контейнера: обращение ВМ к собственному публичному IP недоступно.
Проверка на ВМ проходит через `127.0.0.1:443` с настоящим доменом и обычной
проверкой TLS-сертификата; GitHub дополнительно проверяет публичный DNS-маршрут.

CMS пересобирается при изменении `apps/cms` или `docker/cms`. До её переключения
создаётся и проверяется внешняя резервная копия. Web пересобирается для каждого
одобренного коммита. При перезапуске контейнера возможен короткий перерыв.

Ошибка сборки оставляет старый сайт запущенным. Ошибка readiness или публичной
проверки возвращает предыдущие контейнеры. Незавершённая операция восстанавливается
по журналу после перезапуска службы. Откат контейнеров **не откатывает схему/данные
БД**: несовместимые миграции Strapi требуют отдельного плана и окна работ.

GitHub каждые 10 секунд читает `https://ncfg.ru/deployment-status.json`.
Этот JSON обслуживается самим Caddy независимо от контейнера сайта. Он содержит
только SHA, состояние, этап, время, код ошибки и числовые показатели диска;
исключения, логи, конфигурация и секреты в него не копируются. Ответ имеет
`Cache-Control: no-store` и `X-Robots-Tag: noindex, nofollow`.

Ошибка нужного SHA сразу завершает шаг Actions с аннотацией и кратким отчётом;
при нехватке диска в них указаны свободный и требуемый объёмы. Старые ошибки
других SHA игнорируются. Если supervisor не подтвердил запуск или канал статуса
пропал на 3 минуты, ожидание завершается явной ошибкой. Для активной сборки
сохраняется общий лимит 40 минут. Таймер ВМ может добавить до минуты до начала
проверки нового релиза.
Статус обновляется при смене этапов, а не как heartbeat: при аварийной остановке
процесса без записи ошибки последняя стадия может оставаться `running` до общего
таймаута. Обычные исключения, включая недостаток места, публикуются сразу.

Успех требует состояния `succeeded`, точного SHA на
`https://ncfg.ru/deployment.json` и health сайта и CMS. Поэтому зелёный workflow
подтверждает публичный запуск, а не только передачу задания. Отправка тестовых
писем и заявок не производится.

## Управление

```sh
sudo systemctl status ncfg-autodeploy.timer ncfg-autodeploy.service
sudo journalctl -u ncfg-autodeploy.service -n 30 --no-pager
sudo cat /srv/ncfg/autodeploy/active.json
sudo cat /srv/ncfg/autodeploy/failed.json
```

В журнал попадают только этапы, SHA и тип ошибки. Подробные логи сборки находятся
в `/srv/ncfg/autodeploy/{web,cms}-build.log` и доступны только root. Не публиковать
их целиком: сборка может содержать данные CMS, даже если токен замаскирован.

Остановить новые публикации: `sudo systemctl stop ncfg-autodeploy.timer`.
Уже выполняющийся деплой продолжится; не прерывать его в момент переключения.
После исправления сбоя оператор сохраняет `failed.json` под архивным именем и
повторно запускает службу. Повторный workflow того же SHA сам по себе не удаляет
зафиксированную ошибку и не запускает очистку каждую минуту. Новые коммиты
разрешены независимо от старого сбоя.
Предыдущие контейнеры и исходники сохраняются; следить за местом на системном диске.
Не применять общий `docker system prune` и не удалять данные PostgreSQL.

Supervisor установлен отдельно: `/usr/local/lib/ncfg-autodeploy/deploy.py`.
Изменение этого файла в Git не обновляет службу автоматически. Его новую версию
сначала проверяют тестами и устанавливают через административный SSH-доступ.

При обновлении с версии без публичного статуса сначала на ВМ запускают
`sudo python3 install_status.py`, затем устанавливают проверенный `deploy.py`
с сохранением прежнего файла для отката. Установку supervisor выполняют между
деплоями: останавливают только timer, убеждаются, что service завершён, и
используют `/srv/ncfg/autodeploy/deploy.lock`. После обновления запускают службу
для публикации статуса текущего SHA, возвращают timer и проверяют его состояние.
До push нового workflow проверяют
статус текущего SHA через HTTPS. Полный `install.sh` нужен при первоначальной
настройке; для обновления supervisor builder пересоздавать не требуется.

`install_status.py` принимает только известную конфигурацию production Caddy,
проверяет кандидата, сохраняет приватную резервную копию и добавляет ровно один
маршрут JSON. Он использует существующий bind mount `/config`, сохраняет inode
Caddyfile и применяет конфигурацию через SIGUSR1 (Caddy 2.11+). Контейнер Caddy
не перезапускается, admin API остаётся выключенным. При ошибке проверки
восстанавливается прежняя конфигурация. Повторный запуск сохраняет текущий статус.

Локальная проверка контракта ошибки, отката конфигурации и ожидания Actions:
`python3 -m unittest discover -s infra/cloudru/autodeploy -p 'test_*.py'`.
Для проверки нехватки места используются тестовые значения; заполнять диск
production или публиковать фиктивную ошибку в рабочем endpoint не нужно.

Изменения лимитов/конфигурации BuildKit требуют пересоздать только builder
после окончания сборки: `docker buildx rm --keep-state ncfg-autodeploy`, затем
повторить `install.sh` с профилем `DOCKER_CONFIG=/etc/ncfg/autodeploy-docker`.
Кеш при этом сохраняется; рабочие контейнеры приложения не пересоздаются.
Workflow перед ручным запуском должен быть выбран на ветке `main`.

DNS и Postbox остаются в Yandex; production-развёртывание больше не использует
Yandex Serverless/Registry/Lockbox. Существующие preview/служебные workflows
не входят в этот production-деплой.

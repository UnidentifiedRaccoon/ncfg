# Единый форменный слой (site forms)

Краткое описание для PR и ручной проверки.

## Что сделано

- **Общий UI-слой** (`shared/ui/form`): стили полей (`formInputClassName`, `formTextareaClassName`), подписи (`FormFieldLabel`), баннер ошибки (`FormErrorAlert`), блок согласия с политикой (`FormPrivacyConsent`).
- **Общая логика форм** (`features/form-core`): тексты валидации (`FORM_VALIDATION_MESSAGES`), `EMAIL_REGEX`, валидаторы `validateLeadBasics`, `validateDiagnosticContact`, `validateBlogQuestion`, единый `postJsonOrThrow` для JSON POST с разбором `{ error?: string }`.

## Архитектура: что общее, что сценарное

| Общее | Сценарное (остаётся в виджете/фиче) |
|--------|-------------------------------------|
| Внешний вид полей, ошибки, чекбокса согласия | Разметка секций, заголовки, копирайт кнопок |
| Повторяющиеся правила (email, обязательные поля, consent там, где нужен) | Специфичные поля (вакансия: файл/комментарий; блог: вопрос + контекст статьи; диагностика: опрос + превью + submit) |
| Один способ отправки JSON и ошибок API | URL маршрутов `/api/...`, тела запросов и схемы ответов по-прежнему задаются в сценарии |
| — | Аналитика (`reachGoal` / `YM_GOALS`) вызывается в тех же местах, что и раньше |

**Почему так:** FSD допускает общие примитивы в `shared` и сквозную доменную логику форм в `features`. Виджеты и фичи не тянут лишнего «вверх»; дублируется только то, что по смыслу уникально для сценария.

## Где лежит модуль

- `apps/web/shared/ui/form/` — визуальные примитивы и классы.
- `apps/web/features/form-core/` — валидация, сообщения, `postJsonOrThrow`.

## Миграция: список мест

| Сценарий | Файл |
|----------|------|
| Лид-форма | `widgets/LeadForm/LeadForm.tsx` |
| Вопрос в статье блога | `widgets/Post/PostQuestionForm.tsx` |
| Отклик на вакансию | `features/VacancyApplicationForm/ui/VacancyApplicationForm.tsx` |
| Диагностика (контакт перед отправкой) | `features/diagnostics/hooks/useDiagnosticSurvey.ts` (валидация контакта), `features/diagnostics/ui/DiagnosticSurvey.tsx` (UI блока контакта) |

Валидация вакансии по полям вакансии по-прежнему в `shared/lib/vacancy-application` (сценарная бизнес-логика); к ней добавлены общие обёртки и отправка через `postJsonOrThrow`.

## До / после (дублирование)

| Область | До | После |
|---------|-----|--------|
| Классы инпутов / textarea / label | Повторялись в 3–4 компонентах | `shared/ui/form/styles` + компоненты |
| Тексты «заполните поле» / email / согласие | Разрозненные строки | `FORM_VALIDATION_MESSAGES` + валидаторы в `form-core` |
| `fetch` + `Content-Type` + разбор ошибки | Копипаст с мелкими отличиями | `postJsonOrThrow` |
| Блок согласия с политикой | Дубли UI | `FormPrivacyConsent` (варианты `lead` / `compact`) |

Поведение loading / error / success и контракты API не менялись намеренно; меняется только способ вызова общих частей.

## Как добавить новый вариант формы

1. **UI:** импортировать `FormFieldLabel`, `FormErrorAlert`, `FormPrivacyConsent`, при необходимости `formInputClassName("md" | "lg" | "xl")` из `@/shared/ui/form`.
2. **Валидация:** либо использовать готовые `validate*` из `@/features/form-core`, либо добавить новую функцию в `features/form-core/validation.ts` и экспорт в `index.ts`, если правила переиспользуемые; сценарные правила — рядом с фичей.
3. **Отправка:** вызывать `postJsonOrThrow("/api/...", body)` из `@/features/form-core`; URL и тело — как требует ваш route handler.
4. **Аналитика:** подключать `reachGoal` / цели в том же компоненте или хуке, где была бы логика submit (как в существующих формах).
5. **Границы FSD:** не импортировать `widgets` из `entities`; `form-core` не импортировать из `widgets`. Новая форма в `widgets/*` или `features/*` в зависимости от слоя страницы.

## Ручная проверка (минимум)

- [ ] Лид-форма: успешная отправка; пустые обязательные поля; неверный email; без consent (если обязателен); повтор после ошибки; mobile + desktop.
- [ ] Форма вопроса в статье блога: то же по негативным сценариям и успеху.
- [ ] Отклик на вакансию: успех и негативные кейсы по правилам вакансии.
- [ ] Диагностика: пройти до контактного шага, отправить результаты; ошибки контакта (email, consent).
- [ ] Убедиться, что цели Метрики срабатывают как раньше (submit/start/expand где применимо).

## Критерии приёмки (чеклист)

- [ ] Все четыре сценария используют общий слой (`shared/ui/form` + `features/form-core` там, где уместно).
- [ ] Нет дублирования базовой form-логики (стили, общие валидаторы, JSON POST) между сценариями.
- [ ] Нет визуальных регрессий без отдельного согласования.
- [ ] Loading / error / success работают как прежде.
- [ ] API-контракты тел запросов и ответов сохранены; аналитика не удалена и не ослаблена.

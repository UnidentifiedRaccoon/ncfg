Разделы ниже описывают требования и состояние на дату планирования, включая прежние зависимости и впоследствии удалённые компоненты. Для текущей реализации используйте исходники и отчёты, а не таблицу первоначального аудита.

## 1. Задача и подтверждённые решения

Цель — привести анимации сайта к одной системе на Motion: согласовать поведение и темп, заменить разрозненные реализации и добавить выразительность там, где она помогает прочитать страницу или понять действие.

Основная аудитория — частные лица, HR/L&D и корпоративные заказчики. Анимация должна поддерживать выбор программы, чтение материалов и отправку заявки. Визуальная основа остаётся проектной: тёмно-синий, голубой, стеклянные поверхности, сдержанная профессиональная подача. Авторитетные источники — [PRODUCT.md](../PRODUCT.md), [DESIGN.md](../DESIGN.md), существующие компоненты и токены.

| Решение | Подтверждено пользователем | Следствие для реализации |
| --- | --- | --- |
| Охват | Главная как пилот, затем весь публичный сайт, диагностики и финансовая игра | Выполнить все этапы: пилот задаёт общие приёмы, затем они распространяются на остальные страницы |
| Выразительность | Заметные переходы интерфейса и одна основная сцена, связанная со скроллом | На главной одна основная сцена; остальные блоки используют согласованные переходы без дополнительных постановочных эпизодов |
| Граница Motion / CSS | Motion для содержательных анимаций; CSS для простых hover, focus и изменения цвета | Перенести reveal, смену состояний, раскрытия и прогресс в Motion; простые эффекты контролов сохранить в CSS |
| Зависимости | Базовый план обходится Motion | Реализовать выбранный сценарий средствами базового Motion; Motion+, Anime.js, GSAP и Three.js в объём не входят |

**Рекомендации автора плана для исполнения:** сохранить текущую мобильную композицию, уменьшить перемещения и последовательные задержки, отключить параллакс; основную сцену разместить в hero. Пользователь подтвердил характер анимаций, но не выбирал конкретный storyboard или мобильный сценарий. Эти детали предложены как рабочие решения и уточняются на пилоте по качеству чтения, адаптивности и производительности. Повторное согласование четырёх решений из таблицы для начала работы не требуется.

## 3. Целевая система анимаций

### Назначение и темп

Покрытие означает, что каждая существующая анимация получила решение: перенесена в Motion, обоснованно оставлена в CSS или удалена как лишняя. Это не требование заставить двигаться каждый текстовый блок.

Использовать небольшое число повторяемых приёмов. Согласовать их с текущими токенами DESIGN.md; приведённые ниже значения — стартовые для пилота, затем зафиксировать итоговые значения в одном месте.

| Приём | Где применять | Начальные параметры |
| --- | --- | --- |
| Отклик действия | Кнопка, кликабельная карточка | 120–180 мс; подъём 2–4 px или небольшой scale, без изменения размеров соседей |
| Смена содержимого | Вкладка, отзыв, шаг формы | 200–300 мс; короткий fade и при необходимости смещение 8–12 px |
| Раскрытие | Меню, аккордеон | 250–350 мс; закрытие немного быстрее открытия |
| Появление группы | Карточки секции ниже первого экрана | 350–450 мс; смещение 12–18 px, stagger 40–60 мс с ограничением общей задержки примерно 200 мс |
| Основная сцена | Декоративный слой hero | Прогресс от положения скролла; диапазон эффекта ограничен hero, без таймера бесконечного повторения |

Не использовать одинаковое появление всей секции и всех её карточек одновременно. У одного CSS-свойства должен быть один владелец: если transform управляет Motion, убрать CSS transition-transform/transition-all и hover-transform с того же узла. CSS focus-visible должен оставаться немедленным и понятным.

На длинных текстовых, юридических страницах и в формах движение минимально. Чтение текста и ввод ответа не требуют анимации каждого абзаца или поля.

### Архитектура

1. Сохранить серверные страницы, layout и загрузку данных. Клиентский provider принимает серверные children; компоненты с анимацией получают небольшие клиентские границы. Не ставить use client на всю главную ради анимаций.
2. Перейти на одну прямую зависимость motion и импорты motion/react. Сначала выбрать и проверить совместимую версию в major 12, близкую к текущему lockfile; переход на новый major не смешивать с этой задачей. Текущий официальный guide уже описывает и версию 13, поэтому слепой install latest расширит объём миграции. [Официальный upgrade guide](https://motion.dev/docs/react-upgrade-guide).
3. Подключить MotionConfig с reducedMotion="user". Он отключает transform/layout-анимации, но сохраняет opacity/color. Таймеры, циклы, CSS и программную прокрутку обработать отдельно. [Правила доступности Motion](https://motion.dev/docs/react-accessibility).
4. Оценить LazyMotion + m для общего клиентского слоя. Базовый domAnimation подходит переходам, выходам и жестам hover/tap/focus; layout/drag требуют domMax. Загружать дополнительные возможности только там, где они реально нужны. Не объявлять экономию без измерения: отложенная загрузка меняет начальную стоимость, а не отменяет загрузку функций. Если выбран LazyMotion strict, сначала перевести все обычные motion-компоненты внутри его границы, иначе strict вызовет ошибку. [Руководство по размеру сборки](https://motion.dev/docs/react-reduce-bundle-size).
5. Рекомендуемые новые модули: shared/lib/motion с токенами и рецептами; shared/ui/MotionProvider; shared/ui/Reveal. Проверить принятую в репозитории структуру экспортов и FSD. Не создавать универсальный движок, JSON-DSL или фабрику всех HTML-тегов.
6. Reveal сделать управляемым компонентом с явным применением. Section оставить серверной структурной обёрткой. При поэтапной миграции старый observer обслуживает только ещё не перенесённые маркеры, а новый компонент не получает такой маркер.
7. Серверная разметка, первый экран, ссылка из hash и сфокусированный элемент должны быть видимы. Не отдавать важный текст с initial opacity:0 в ожидании клиентского эффекта. Для появления ниже экрана допустима подготовка скрытого состояния после hydration только у элементов, достоверно находящихся вне viewport; при ошибке или отключённом движении остаётся статичный контент. Проверить медленную загрузку клиентского кода.
8. Счётчики и непрерывные значения скролла вести через MotionValue, без React setState на каждом кадре. UI-state описывает смысловые состояния: открыто меню, выбран отзыв, активен вопрос. Анимационный callback не должен быть единственным источником бизнес-состояния.

## 4. Сценарий главной страницы

Текущая последовательность берётся из главной страницы (архивный путь: `apps/web/docs/</Users/yura-posledov/Codex/ncfg/apps/web/app/(site`)/page.tsx>): Hero → MissionLedgerAlliance → Services → Products → Projects → Partners → LeadForm → News → Footer. Team и HowWeWork находятся на других страницах и не должны внезапно добавляться на главную ради демонстрации Motion.

| Блок | Предлагаемое поведение | Ограничение |
| --- | --- | --- |
| Header | Плавное открытие/закрытие подменю и мобильной панели; короткий переход визуального состояния | Сохранить sentinel и существующий расчёт тона. Ссылка «Компаниям» и кнопка раскрытия остаются разными действиями |
| Hero | На desktop изображение/декоративный слой слегка смещается и масштабируется при выходе hero из viewport; текст и CTA доступны сразу | Начальный диапазон для пилота: до 24 px и scale 1→1.03. Не менять порядок контента, не задерживать LCP, не превращать весь экран в закреплённую сцену |
| Hero до 1200 px | Использовать существующий вариант без изображения; короткий эффект только для подходящих декоративных элементов | Не добавлять desktop-картинку в мобильную версию и не запускать эффект в скрытом варианте hero |
| MissionLedgerAlliance | Сохранить колоду; согласовать easing, длительность и прерывание переходов при повторных нажатиях | Не связывать смену карточек со скроллом поверх существующего управления |
| Services / Products / Projects | Короткое появление видимой группы карточек, единый отклик кликабельных карточек | Суммарная задержка ограничена; нажатие доступно сразу; длинные списки не выстраиваются в длинную очередь |
| Partners | Смена категории/отзыва через управляемый переход; Motion-прогресс, если сохраняется автопереключение | Разделить таймер и визуальную шкалу; предусмотреть остановку и ручное управление |
| LeadForm | Понятная смена отправки, ошибки и успеха; при необходимости локальный переход высоты | Состояние формы и введённые данные не теряются при анимации; срочная ошибка появляется без задержки |
| News | Тот же приём карточек, что у других каталогов | Не вводить ещё один тип движения для похожей задачи |
| Footer | Сохранить спокойным; использовать общие эффекты интерактивных ссылок | Не добавлять отдельную постановочную сцену в завершение страницы |

Hero — рекомендуемое место для единственной основной сцены на главной. В пилоте оценить её на реальном изображении и контенте и подобрать заметный, но не мешающий чтению диапазон. Если движение ухудшает композицию, скорректировать слой или амплитуду, сохраняя одну сцену, управляемую скроллом, в обычной desktop-версии. Для reduced motion и мобильного варианта использовать описанное упрощение.

Визуальный ориентир для связи эффекта со скроллом — [официальная демка Scroll zoom hero](https://examples.motion.dev/react/scroll-zoom-hero). Использовать её как референс поведения, а реализацию писать под текущую композицию NCFG. Установка платных компонентов и копирование недоступного исходника в план не входят.

## 6. Критерии приёмки

**Поведение и доступность**

- На главной в обычном desktop-режиме есть одна заметная сцена, управляемая скроллом. Остальные содержательные анимации используют общие приёмы Motion; простые hover, focus и изменения цвета остаются в CSS. Дополнительные библиотеки и платные компоненты для выполнения плана не нужны.
- Статичный контент первого экрана и CTA публичных страниц видны сразу; ниже экрана текст доступен при отключённом JavaScript и при медленной загрузке анимационного кода. Для диагностик и игры сохранить существующую модель загрузки и доступности: миграция анимаций не требует переписать их для работы без JavaScript. Новая анимация не ухудшает существующий статичный fallback.
- При prefers-reduced-motion нет параллакса, пространственных вступлений, декоративных циклов и автопереключения Partners. Проверить также изменение системной настройки в открытой странице, а не только начальную загрузку.
- В меню, аккордеоне, форме и игре нет фокуса в невидимом содержимом. Управление клавиатурой, Escape, возврат фокуса и touch сохраняются.
- Быстрые open/close, следующая/предыдущая карточка, повторная смена вкладки и переход назад не оставляют промежуточное состояние, пустой блок или второй активный экран.
- Ответы диагностик, данные заявок и состояние игры сохраняются. Ошибки валидации доступны сразу. Тестовые действия с реальными отправками, CRM и почтой не выполнять.
- Hash-навигация, прямой вход, back/forward и смена маршрута не скрывают целевой контент и не запускают второй reveal уже показанного элемента.

**Производительность**

- Нет React-render на каждом кадре только ради декоративного счётчика или скролла; исключения, если понадобились, объяснены и измерены.
- Нет постоянно работающих декоративных таймеров/кадровых циклов в скрытой вкладке или вне viewport. Подписки и анимации освобождаются при unmount и смене зависимостей.
- Нет двойного управления transform и массового layout на всей длинной странице. Анимации высоты меню/аккордеона проверены локально; широкие blur/filter-эффекты не используются как универсальный приём.
- В одинаковых условиях сравнить исходную и итоговую загрузку, клиентские чанки, LCP/CLS и отклик основных действий. Исследовать воспроизводимое ухудшение; не выдавать размер библиотеки из документации за размер маршрута и не обещать 60 FPS без измерения.
- Для финального сравнения сборки использовать production-режим по правилам проекта; dev-режим подходит для поведения, но не для заключений о весе и скорости production. Если корректный замер недоступен, это явно отмечается в результате.

**Проверки и свидетельства**

- Обычный старт — npm run dev из корня; при сбое npm run dev:doctor. Соблюдать [DEVELOPMENT.md](../../../DEVELOPMENT.md), не поднимать локальную CMS или Docker ради frontend-миграции.
- После серии изменений выполнить из apps/web: npx --no-install tsc --noEmit. Запустить релевантные проверки ESLint и существующие тесты через npm test. Эти проверки выполняются для изменённого кода, отдельно от readiness локального запуска.
- Не создавать тесты, которые только повторяют значения props анимации. При изменении логики таймера, выбора шага или сохранения состояния добавить проверку соответствующего поведения. Для визуальных переходов использовать browser QA.
- Проверить главную при ширинах около 390, 768, 1199, 1200 и 1440 px, по одному представителю каждого затронутого публичного шаблона, обе диагностики и финансовую игру. Использовать доступные Chrome и Safari/WebKit; отсутствующую проверку обозначить, не считать пройденной.
- Предоставить записи обычного движения на desktop/mobile и reduced motion, список проверенных маршрутов и результаты команд. Для производительности приложить сопоставимые наблюдения до/после и условия измерения.
- Изменения не затрагивают бизнес-контракты CMS/API, содержание предложений, SEO-метаданные и публичные URL, кроме обязательных правил нового экспериментального маршрута.

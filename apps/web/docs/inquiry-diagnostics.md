# Диагностика пути к заявке, схема 2

Счётчик НЦФГ: `108387180`. Код подготовлен 12.09.2026; сбор новой схемы в production начинается только после выкладки. Не объединять её с предыдущими периодами без отметки о смене измерения.

Корпоративный сценарий: задача → раскрытая программа → «Обсудить эту программу» → форма с выбранной программой → отправка запроса. Можно выбрать «Помогите выбрать программу». Контакты сохраняются при смене программы и после ошибки. Программа добавляется отдельной первой строкой в `message` существующего `/api/lead`, поэтому доходит до всех существующих приёмников без нового API-контракта. Футер корпоративных страниц ведёт к местной форме. На странице отдельной услуги её название включается в обращение автоматически.

| Событие | Условие | Учёт | Настройка счётчика |
|---|---|---|---|
| `lead_form_view` | Не менее половины заголовка карточки формы видно в активной вкладке | Один раз на экземпляр обращения | Создана, ID `612229586` |
| `lead_form_start` | Фокус внутри формы; сохранён старый триггер | Один раз на экземпляр обращения | Существующая, ID `544431463` |
| `lead_form_input` | Пользователь изменил текстовое поле до непустого значения | Один раз на экземпляр обращения | Создана, ID `612229766` |
| `lead_program_select` | Выбор программы через CTA карточки или селект в форме, включая сброс выбора | Каждое действие | Создана, ID `612234466` |
| `lead_form_attempt` | Отправка формы, до клиентской валидации | Каждая попытка; повтор во время запроса подавляется | Создана, ID `612229768` |
| `lead_form_error` | Валидация, неуспешный HTTP-ответ, неподтверждённый ответ либо сетевая ошибка | Одно событие на неуспешную попытку | Создана, ID `612234334` |
| `lead_form_submit` | HTTP 2xx и JSON `{ success: true }` от `/api/lead` | Один раз на экземпляр обращения | Существующая, ID `544420357` |

Новые цели имеют тип «Целевое событие», условие **«Совпадает»** с идентификатором; без статического дохода и без включения в избранные. Не использовать сумму всех диагностических целей как успех бизнеса. `lead_form_start` продолжает означать фокус, включая фокус кнопки или согласия, а не ввод текста. Сравнивать реальный ввод следует по новой отдельной цели.

Параметры отправляются по явному списку:

| Параметр | Значение |
|---|---|
| `schema_version` | `2` |
| `form_type` | `corporate` для форм на корпоративных страницах, `general` для общей формы |
| `form_id` | `lead-form` |
| `form_instance_id` | Случайный идентификатор текущего обращения; не cookie и не постоянный ID посетителя |
| `sequence` | Порядковый номер события внутри экземпляра формы |
| `attempt` | Номер попытки, начиная с 1; до первой попытки — 0 |
| `page_path` | Путь страницы без query и hash |
| `program_id` | ID выбранной программы/услуги либо `unspecified` |
| `company_provided` | Только признак заполненности поля компании |
| `error_code` | Одна из категорий ниже, только при ошибке |
| `invalid_fields` | Имена некорректных обязательных полей, без значений |
| `http_status` | HTTP-статус неуспешного ответа, если получен |
| `request_id` | Неперсональный ID из заголовка API для сверки с серверным журналом, если получен и прошёл проверку формата |

Категории ошибок: `required_fields`, `invalid_email`, `consent_required`, `request_rejected` (прочие HTTP 4xx), `rate_limit` (429), `server_error` (5xx), `invalid_response` (2xx без подтверждения), `network_error` (ответ не получен). Текст ошибки сервера не выводится пользователю и не передаётся в Метрику. Контакты и сообщение не попадают в параметры новых событий. Произвольные UTM-параметры в события формы не копируются; источники и кампании анализируются штатными разрезами Метрики.

`form_type=corporate` описывает форму и контекст страницы, а не подтверждённую принадлежность человека компании. `company_provided=true` тоже не является квалификацией. Обращения с главной остаются `general`, даже если их отправил HR. Отклики кандидатов по-прежнему можно отличить по `vacancy_slug`; их форма не переведена на новую диагностику. Доставку, дубли и коммерческое качество нужно сверять в приёмнике обращений. Успех `/api/lead` не гарантирует успешную дополнительную синхронизацию в каждую CRM.

CTA получили `page_path` и `cta_location` (`hero`, `header`, `footer`, `program`, `task_navigator`), где место размечено. У выбора программы есть `program_id`. Переход из навигатора задач к описанию фиксируется как `service_click`; он не означает выбор этой программы для обращения. Якорь раскрывает соответствующую карточку и переводит фокус на её заголовок. Уже выбранная программа передаётся в форму отдельным действием CTA.

Для анализа использовать полный знаменатель по заданной аудитории и периоду. Основной путь формы: `lead_form_view` → `lead_form_input` → `lead_form_attempt` → `lead_form_submit`. CTA необязателен для тех, кто сам дошёл до формы. Последовательность проверять внутри одного визита/экземпляра по `form_instance_id` и `sequence`; попытки связывать по `attempt`. Пересечения независимых итоговых счётчиков не являются последовательной воронкой. Не складывать посетителей по страницам или дням. При выбранной цели проверять, не исключила ли таблица строки без конверсий из знаменателя.

Локальная проверка не отправляет события в production: канонический launcher обнуляет ID счётчика и отключает внешние эффекты. Только в development `reachGoal` публикует браузерное событие `ncfg:analytics` с тем же payload для тестового слушателя. `/experiments` исключены и из этого канала. Ошибка или блокировка SDK не должны менять результат отправки формы.

Проверки логики из `apps/web`:

```sh
node --import tsx --test features/inquiry-diagnostics/model/diagnostics.test.ts shared/lib/ym.test.ts
npx --no-install tsc --noEmit
```

Браузерные тесты должны перехватывать `/api/lead` и возвращать контролируемые ответы, не отправляя реальные обращения. Проверять: раскрытие программы, передачу выбора, отсутствие обязательности выбора, фокус без ввода, обязательные поля, согласие, HTTP/сетевые ошибки, сохранение данных, блокировку повторной отправки, видимое подтверждение и новый экземпляр после «Отправить ещё». После выкладки отдельно подтвердить получение новой схемы счётчиком; локальный тест этого не доказывает.

Проверка 12.09.2026: семь тестов логики, TypeScript и ESLint затронутых модулей прошли. В установленном Chrome через Playwright сезонный сценарий прошёл при 1440×1000 и 390×844, без ошибок браузера. Ответы `/api/lead` перехвачены: обязательные поля, email, согласие, HTTP 503/429, неверный JSON, обрыв сети, успешный ответ, повторное обращение. Реальные заявки не отправлялись. Исправлено внутреннее смещение блока подтверждения при фокусе на мобильном: `overflow-clip` сохраняет обрезку фона, не создавая прокручиваемого контейнера. Проверка общей `/companies` ограничена локальным HTTP 500 из-за таймаута Strapi; её браузерный сценарий ещё нужно подтвердить при доступной CMS.
